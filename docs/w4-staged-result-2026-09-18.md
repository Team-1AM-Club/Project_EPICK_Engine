# W4 전체 흐름 구현·비교·연결 검증 결과

**원문 추출 → 문항·기업 조건 판단 → 근거 검사 → 추천 → W1 형식 저장까지 실제 로컬 모델로 시연했다.** Gemma 12B 추출 → Gemma 26B 판단 조합이 HTTP와 W1 합성 Run 시연에서 통과했다. **운영 모델 확정과 실제 팀 서버·PostgreSQL 연결은 완료되지 않았다.** 모든 모델에 남은 오류가 있어 운영 선정은 `WITHHELD`다.

## 각 단계가 하는 일

| 단계 | 현재 구현 | 의미 |
| --- | --- | --- |
| 1. 기업 정보 수집·검증 | W3 C01 정보를 받아 출처·버전·유효기간·제한·조건 트리를 검사 | 회사 정보를 새로 수집하는 주체는 W3. W4는 전달된 근거가 지금 사용 가능한지 확인 |
| 2. 경험 선택 기준 정리 | 문항 5개·내용 점검 10개 초안, 회사 Claim과 Requirement 분리 | 문항이 요구하는 내용과 회사의 별도 조건을 섞지 않음 |
| 3. 원문 근거 추출 | Gemma 12B가 역할·행동·결과·기간과 본인/타인·계획/완료를 분류 | 코드가 원문 구간과 위치를 고정하고, 모델은 그 구간을 분류 |
| 4. 적합성 판단·검사 | 문항 / 회사 진술 / 세부 조건을 별도 호출. 코드가 인용·주체·서술 상태를 검사 | 기존 도구 사용을 학습으로 확대하거나 동료의 행동을 본인 것으로 추천하는 오류를 줄임 |
| 5. 추천·백엔드 연결 | 코드가 순위와 이유·확인 질문을 반환하고 W1 후보 형식으로 변환 | LLM이 임의로 점수를 붙여 순위를 정하지 않음. 상세 원문 근거도 별도 보존 |

기업 기준이 있는 경험 하나에는 추출 1회와 판단 3회, 총 4회 호출한다. 데이터가 커지면 검색으로 후보를 줄이는 앞단이 필요하다. 현재 원문 입력은 최대 20개이며 실제 Graph·Vector 검색과 연결한 대규모 검증은 남아 있다.

추천 순서는 문항 전체의 근거 상태 → 지원 근거의 종류 수 → 경험 ID다. 세부 점검 개수나 기업 연결 개수를 추가 점수로 중복 계산하지 않는다. 동점에서 경험 ID로 앞선 것은 능력이 더 뛰어나다는 뜻이 아니다.

## 새 가상 사례 6개, 네 모델 실제 비교

모델 호출 전에 사례·정답 초안·프롬프트를 고정했다. 수족관 일지 개발, 도서 검색 개발, 일본어 안내, 기존 프로그램 반복 실행, 미래 학습 계획, 동료의 개발을 평가했다. Gemma 12B가 실제 추출한 동일 결과를 네 판단 모델에 전달했다. 이 기업 조건은 명시적인 가상 자료이며 SK하이닉스가 실제 제시한 조건이라고 주장하지 않는다.

채점은 JSON 구조, 문항 의미, 회사 진술 연결, 개별 조건, 필요한 원문 인용, 코드 검사 후 전달 결과를 분리했다. 관련 문맥을 함께 인용해도 인정하되 필수 근거 구간은 포함해야 한다. 미기재의 `NOT_SHOWN`과 보수적인 `AMBIGUOUS`는 허용하지만, 근거 없는 `SUPPORTED`나 미기재를 반대로 단정하는 `CONTRADICTED`는 오답이다. 과거 점수는 고치지 않았다.

| 판단 모델 | 문항 의미 18개 | 회사 진술 6개 | 세부 조건 18개 | 근거 인용 42개 | 코드 검사 후 회사 판정 24개 | 엄격한 기준 |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| Qwen 3.5 9B | 94.44% | 100% | 100% | 97.62% | 100% | 미통과 |
| Qwen 3 14B | 88.89% | 100% | 88.89% | 90.48% | 100% | 미통과 |
| Gemma 4 12B | 94.44% | 100% | 83.33% | 90.48% | 87.50% | 미통과 |
| Gemma 4 26B A4B | 94.44% | 100% | 88.89% | 92.86% | 91.67% | 미통과 |

네 모델 모두 JSON 구조는 6/6 정상이다. 코드 검사 후 문항 판정은 모두 18/18 맞았지만 **모든 모델이 미래 학습 계획을 한 번씩 실제 학습으로 긍정**했다. 코드가 계획 근거를 보고 `AMBIGUOUS`로 낮춘 것이다. 이 보호 동작을 모델 자체의 정답으로 바꾸어 채점하지 않았다.

Gemma 계열은 동료의 행동이나 다른 분야의 행동에 대해 단순 미기재 대신 `CONTRADICTED`로 단정한 오류가 있었다. Qwen 14B는 동료의 행동을 본인 근거로 긍정한 오류도 있었고 코드가 낮췄다.

추출은 따로 채점했다. Gemma 12B의 원문 21구간 완전 일치 **19/21(90.48%)**, 종류 F1 **92.59%**, 주체·계획/완료·이슈 판정은 각각 **100%**, 사용할 수 없는 근거의 잘못된 채택은 **0개**였다. 두 불일치는 미래 계획을 `GOAL`로 볼지 `ACTION`으로 볼지의 초안 분류 차이였다. 계획이라는 서술 상태는 보존됐다. 이번 턴에서 추출 모델 네 개를 다시 비교한 것은 아니다.

## 기존 사례와 실제 조합 시연

새 6개에서는 Qwen 9B가 가장 적은 오류를 냈다. 하지만 기존 7개로 돌아가면 코드 검사 후 문항 판정은 Qwen 9B **19/21**, Gemma 26B **21/21**이었다. 회사 판정은 각각 **28/28**, **26/28**이었다. 따라서 단일 모델이 모든 영역에서 최고라고 결론내리지 않았다.

기존 7개는 이미 본 개발 사례다. 인용 범위와 불확실성 정책을 새 규칙에 맞춰 **호출 전에** 정리해 회귀 검사했으며, 이를 새로운 미관측 평가로 세지 않았다. 이전 실제 추출 7회를 그대로 재사용했고 새 판단 42회를 실행했다.

| 실제 실행 | 모델 조합 | 확인 결과 |
| --- | --- | --- |
| HTTP 추천 시연 | Gemma 12B 추출 → Gemma 26B 판단 | HTTP 200, 고정 3경험 품질 검사 통과 |
| W1 첫 연결 시연 | Gemma 12B 추출 → Qwen 9B 판단 | UUID 대응·저장·DTO 검사는 통과. 달리기를 지속 학습으로 판단해 의미 품질 검사 실패. 기록 보존 |
| W1 보완 확인 | Gemma 12B 추출 → Gemma 26B 판단 | 실제 추론 12회, 3후보 DTO·품질 검사 통과. 중복 실행 추가 호출 0회, 철회 후 조회 차단 |

Gemma 12B → Gemma 26B는 **고정된 작은 시연을 보여 줄 조합**이다. 공식 선정된 운영 모델이나 전체 성능 최고 조합이라는 뜻은 아니다. 정답은 작성자 초안이고 사람 검토 전이다. 반복은 1회이며 다른 문항·긴 원문·실사용 분포의 일반 성능을 대표하지 않는다. GPU 사용 상태가 달라 속도 우열은 이 결과로 판단하지 않는다.

## 검토·검증 결과

- 최종 전체 로컬 테스트 **351개 통과**, 실패·오류·생략 0. 기존 모의 HTTP 시연 2개 통과. 이 회귀 검사의 모의 호출 12회는 실제 모델 평가에 합산하지 않았다.
- 완료한 실행들의 실제 모델 호출 **156회**: 새 평가 78회 + 기존 사례 판단 42회 + HTTP 12회 + W1 첫 시연 12회 + W1 보완 확인 12회.
- 최초 실행기 파일 생성 오류로 중단된 별도 이력의 완료 호출 **12회**는 비교에서 제외했다. 이를 포함한 이번 작업의 실제 요청은 **168회**다. 오류 수정 후에도 입력·프롬프트·정답을 바꾸지 않았다.
- 새 판단 요청 **72개**의 실제 송신 내용을 대조해 동일 추출 결과·모델·프롬프트·출력 Schema가 쓰였음을 확인했다.
- 현재 W1 실제 Pydantic DTO로 최종 후보 3개를 검증했다. 비교한 백엔드 파일 5개는 최신 develop과 동일했다.
- Ruff F 검사와 Git diff 공백 검사 통과. 실행한 로컬 모델 서버는 모두 종료 확인했다.

검토에서 모델·생성 설정 변경 시 캐시 구분, 게시 후 Source 만료·generation 변경 시 조회 차단을 추가했다. 매 판단 호출 전 권한·context를 검사하고, staged 모델 설정을 확인할 수 없으면 캐시를 재사용하지 않는다. 서비스 실행에는 요청·응답 본문 로깅을 껐다. 비교 평가의 상세 기록은 사전 등록된 가상 데이터에만 남겼다.

## 팀에 넘길 내용과 남은 단계

[W1 연결 계약](w4-w1-bridge-contract-2026-09-18.md)의 RunStore를 팀 repository·인증·DB에 연결하면 된다. 현재 시연 DB는 독립 SQLite이며 실제 팀 서버나 PostgreSQL을 호출하지 않았다. 실서비스에 연결하려면 ENGINE Run 접수 경로, 상세 결과·Source 의존성 저장과 게시 트랜잭션, 조회/선택 API의 권한 검사를 적용해야 한다.

정답 초안·문항 대응·상태/정렬 정책은 팀 검토가 필요하다. 네 모델 모두 엄격한 기준 미통과이므로 운영 자동 선택은 보류한다. 공식 지원서의 미확인 문구·글자 수·필수 여부를 고정하지 않았다. 실제 사용자 자료·상용 모델 API·팀 서버 전송은 이번 작업에서 수행하지 않았다.

Git 커밋·푸시·PR·배포와 팀 메시지 발송은 하지 않았다. 이전 GitHub CI 성공은 이전 커밋의 기록이며 이번 351개 결과는 로컬 실행이다.
