## 4. 현재 W4와의 연결 차이

현재 [handoff_contract.py](../epick_w4/handoff_contract.py)의 `KnowledgeBundle`은 W4가 작성한 `w3-w4-projection/0.1-draft`다. W3의 `StructureResponse`는 `status/errors/bundle` 구조이며, 내부에 `evidences/claims/requirements/source_reviews`가 들어간다. 이 응답을 현재 `ServerContext.company_knowledge`에 그대로 넣을 수 없다.

| 차이 | W4에서 보존하거나 결정할 내용 |
|---|---|
| 신호와 기업정보 분리 | 신뢰할 수 있는 호스트가 `source_id`, generation, 정확한 IndexKey, 두 순번과 StructureResponse를 연결. 공개 사용자 요청에 임의 기업정보를 받지 않음 |
| Claim/Requirement 상태 | W3 `FAILED/BLOCKED`와 기존 W4 `REJECTED/WITHDRAWN`의 뜻이 같다고 가정하지 않음. 원 상태와 사유 보존, `VERIFIED`·`USABLE`인 근거만 추천에 사용 |
| 복합 요건 | `AND/OR/LEAF`, root/children, `same_experience_required`, 예외·비교 기준을 보존. 현재 W4의 평면 `statement`만으로 조건을 대체하지 않음. `GENERAL`을 `REQUIRED/PREFERRED`로 임의 치환하지 않음 |
| 근거 위치 | W3 excerpt, artifact_id, native locator, offset, 무결성 범위를 보존. 발췌 해시를 전체 SourceVersion 해시로 대체하지 않음 |
| 채용 범위·날짜·완전성 | 현재 W4가 요구하는 scope/as_of/게시일/원문 해시/필수 자료 여부를 StructureResponse만으로 모두 채울 수 없음. W1/W2/W3 메타데이터의 공급 위치·의미를 대응표로 정하고 누락 상태를 유지. observed_at을 게시일로 쓰지 않음 |
| 자료 부족 상태 | `requirement_presence`, source_reviews, limitations를 전달. 필수 요건 목록이 비어 있다는 이유로 지원 자격 충족을 선언하지 않음 |
| 현재성·무효화 | 두 순번·generation·전체 IndexKey와 현재 사용 가능 상태를 함께 확인. 여러 Source를 조합한 추천은 전체 의존 Source와 W1 사용자/프로젝트 범위를 추적 |

기존 [service_adapter.py](../epick_w4/service_adapter.py)는 문맥 재조회·해시 비교·권한 재검사 지점이 있다. 이 경계에 W3 현재 상태 검사를 연결할 수 있다. 현재는 C01 신호 영속 수신·ACK·복수 Source 결과 무효화가 연결되지 않았다.

기존 W4의 게시일 미상 자료 제외 규칙도 자동으로 변경하지 않는다. 날짜 미상 자료의 사용 범위를 바꾸려면 별도 정책과 회귀 사례가 필요하다. 전체 지원 자격은 현재처럼 `NOT_ASSESSED`를 유지한다.

## 5. A1–A5 회신 초안

아래는 W4 검토 의견 초안이며 사용자/팀의 채택 서명이나 외부 전송 기록이 아니다.

| 항목 | W4 제안 | 실제 W4 채택 완료에 필요한 것 |
|---|---|---|
| A1 데이터 계약 | r2의 signal/StructureResponse/ACK를 연결 기준 후보로 삼는 데 동의 제안 | 위 필드 대응·메타데이터 공급 위치·요건 트리 보존을 명시한 W4 어댑터와 소비 테스트 |
| A2 두 순번·generation | 별도 값으로 보존하는 방향 동의 제안 | Source 단위 restriction 순번 최종 결정, commit/profile 고정, 상태 저장·읽기 검증 |
| A3 차단·복구 | 제한/gap/충돌 시 관련 결과 재사용 차단, 적합한 새 READY 상태로 복구 | 복수 Source 의존성 추적과 재조회 테스트. `cleared`만으로 복구하지 않음; snapshot 후 history_complete=false를 단독으로 영구 차단 조건으로 쓰지도 않음 |
| A4 재전송·ACK | 영속 반영 후 ACK, 중복·응답 유실·재시작 처리 방향 동의 제안 | 실제 W4 저장 트랜잭션과 신호 처리 연결. 차단 신호의 관련 결과 무효화까지 영속 반영한 뒤 ACK. worker 재시도/DLQ 운영 정책 별도 |
| A5 출처·보관·권한 | 전체 IndexKey와 static_html 보존, TTL/현재 권한 검증 방향 동의 제안 | 파생 추천·캐시의 보관/삭제 책임, 운영 TTL, P4/P5 결정. full/normalized_body는 현재 W3 미지원 |

참조 consumer는 Source당 단일 캐시다. 실제 추천 결과의 복수 Source 의존성을 처리하는 완성된 W4 모듈로 간주하지 않는다. 지식 응답의 `COMPLETED/LIMITED`나 Source의 READY만으로 모든 Claim이 검증됐다고 판단하지 않는다.

## 6. 다음 구현 순서와 담당

1. **W4:** 고정한 r2 schema/fixture를 대상으로 입력 대응표를 완성하고, 새 서버 입력 계약과 어댑터 변경안을 작성한다. 원문 해시·날짜·채용 범위 등 없는 정보를 만들어 채우지 않는다.
2. **W4 + 호스트 담당:** 신호 저장과 ACK, 현재 상태 재검사, 전체 Source/사용자 범위별 결과 무효화를 연결한다. 기존 W4의 모델 호출 전·반환 전 권한 검사 경계를 유지한다.
3. **W4:** 실제 추천 흐름에 가상 기업자료와 가상 경험을 넣어 정상/제한/지연/중복/응답 유실/복합 조건/다중 출처/상태 조회 실패 사례를 검사한다. 이때만 실제 W4 consumer 적용 결과로 보고한다.
4. **W3:** W4의 수정 의견을 반영한 동일 commit/profile을 지정한다. **W2/W3:** 실제 producer 산출물·registry·replay/snapshot을 함께 검증한다.
5. **PM/W2/W4:** P4/P5와 보관 정책을 결정한다. **W1:** 개인 권한·삭제·결과 게시 시점의 검사 계약을 제공하고 연결한다.

REAL 입력 허용, 운영 모델 선정, 실제 사용자 데이터의 모델 전송은 이 전달본 검증으로 승인되지 않는다. 기존 CI 256개 통과와 이번 W3 197개 통과를 합쳐 팀 end-to-end 검증 완료로 표시하지 않는다.
