# W4 정답·오류 검토와 v3 재평가

기록일: 2026-09-09. 이전 실제 응답을 검토해 코드·프롬프트·정답 초안을 수정하고 새로운 사례를 고정했다.
검토는 개발 보조 도구가 수행했다. **사람이 검토·승인한 정답으로 표시하지 않으며 모든 기준은 `DRAFT`다.**

이후 요청받은 남은 쟁점의 검토 판정은 [후속 검토 기록](w4-followup-review-2026-09-09.md)에 있다.
custom 표현과 인용 실패가 함께 집계되는 점, 매칭 오채택 수의 진단 범위를 확인했다. 아래 성적은 당시 기준으로 보존했다.

네 모델에 이전 설정 A와 보완 설정 B를 적용해 **비교 640회·별도 시연 106회**를 실제 호출했다.
B에서 문항·매칭 종합 최고점은 Gemma 26B의 77.65점, 추출 전체 일치율 최고는 Gemma 12B의 88.68%다.
Gemma의 추출은 개선됐고 Qwen의 매칭은 저하됐다. 현재 B는 개발 실험 설정으로 유지하며,
추출 12B·매칭 26B를 다음 단계의 검토 후보로 삼는다. **운영 모델 선정과 두 모델을 섞은 통합 호출의 품질 확인은 보류 상태다.**

## 검토 후 바꾼 것

| 확인한 문제 | 조치 | 유지한 경계 |
|---|---|---|
| AI 지시를 이미 제외했는데 `UNCERTAIN` 상태 때문에 경험 전체가 실패 | `INSTRUCTION_IN_SOURCE`·`NO_EVIDENCE`를 제외 사유로 우선 처리 | 해당 구간에 kinds가 있으면 여전히 거부. 지시문을 fact로 만들 수 없음 |
| 상태와 문제 코드가 모순된 JSON | 로컬 출력 스키마에서 정상·확인 필요·제외 상태를 분기 | 문법 제약은 의미 정답을 제공하지 않음. 원문 판단은 모델이 수행 |
| fact 사용 불가라고 하면서 이유가 없거나, 무관하다고 하면서 matches를 반환 | 사용 여부와 issue, `UNRELATED`와 빈 matches의 조합을 스키마로 제한 | 사용 불가 fact의 참조·중복 ID 등은 코드에서 계속 거부 |
| 문항 부합부터 판단하면서 본인 기여·계획 여부를 혼동 | fact 검사 → 기준 연결 → 관련성 순서로 출력. 계획·팀 행동·역할 배정의 처리 지침을 명확히 함 | LLM의 의미 오류를 규칙 추천으로 대체하지 않음 |
| 역할을 설명하라는 지시를 책임감으로 확대, 사용자 관점을 문제 해결에 강제 대응 | 답변 구성 지시와 역량을 구분하고 custom 기준 사용 지침을 구체화 | 주어진 문항에 없는 기업 인재상·역량을 추가하지 않음 |
| 한 구간의 계약 실패가 같은 경험의 다른 오류를 가림 | 추출 평가에서는 식별 가능한 구간을 개별 진단 | 요청의 필수 검증은 여전히 실패. 실제 서비스는 잘못된 응답 전체를 거부 |
| ROLE을 ACTION으로 잘못 늘린 경우 위험 지표에서 빠질 수 있음 | 사용 가능 상태뿐 아니라 정답에 해당 fact 종류가 존재하는지도 검사 | 잘못 추가한 역할·행동·결과를 필수 검사에 포함 |
| 서버 시작 후 클라이언트 생성 실패 시 정리 경계 밖에 있음 | 클라이언트 생성도 서버 종료를 보장하는 `try/finally` 안으로 이동 | 이 실행기가 시작한 서버만 정리 |

프롬프트는 `w4-semantic-grounding/0.3`, `w4-source-unit-extraction/0.3`이며,
로컬 출력 제약은 `input_ids_and_coherent_states/0.3`이다. JSON 필드와 외부 API 입출력 형식은 유지했다.
분기 스키마는 [llama.cpp의 JSON Schema 지원 문서](https://github.com/ggml-org/llama.cpp/blob/master/grammars/README.md)를 참고했고,
설치된 b10859 런타임에서 기존 가상 자료로 실제 호출해 지원 여부를 확인했다.

## 정답 초안의 수정 근거

기존 모델 응답을 보고 변경한 항목은 모두 개발 사례로 분류한다. 새로운 사례의 응답을 보고 정답을 수정하지 않는다.

| 대상 | 기존 초안 | v3 초안과 이유 |
|---|---|---|
| `episode-library-reservation/u9` | ACTION / SELF / PLANNED | ACTION+PERIOD / UNSPECIFIED / PLANNED. ‘다음 학기’가 명시됐고 해당 문장에는 주체가 생략됨 |
| `holdout-raw-future/u3` | ACTION / SELF / PLANNED | ACTION+PERIOD. ‘다음 주’라는 시기 표현 보존 |
| `holdout-raw-context/u1` | ACTION / SELF / MIXED | ACTION+PERIOD. ‘다음 주’ 보존. 완료와 계획의 MIXED·확인 필요는 유지 |
| 사용자 관점 문항 | custom label 하나만 허용 | 같은 관점의 ‘사용자 관점’, ‘사용자 중심 관점’, ‘사용자 중심’을 사전 등록. 문제 해결 등 다른 역량으로 바꾸는 것은 계속 오답 |

시간·주체 수정은 원문의 명시 정보에 따른 개발 판단이다. 한국어의 주체 생략, ACTION과 RESULT의 경계,
사용자 관점과 문제 해결의 구별은 팀원이 검토할 항목으로 남긴다. 한 모델의 출력을 정답으로 복사하지 않았다.
문항·매칭의 50:50 가중치와 기존 필수 기준은 완화하지 않았다.

v2 파일과 실제 결과를 보존했다. 현재 소스에서 이전 자료를 실행하기 위한 프롬프트 해시만 갱신했고,
내용 수정은 별도 `*.v3.draft.json`에 저장했다. v2 실행 코드 24개도
`output/review-v3-20260909/v2-source/`에 복사한 뒤 이전 기록의 SHA-256과 일치함을 확인했다.

## 새 사례와 측정 방식

문항 24개·경험별 판단 44개·원문 경험 12개/53구간을 각 1회 측정한다. 비교 호출은 모델당 80회다.
이 중 **새 문항 8개·새 경험 판단 16개·새 원문 4개/20구간**이 `holdout_v3`이고, 이전 사례는 모두 `development`다.

새 사례는 명시적 미수행, 타인의 조율, 완료와 적용 계획의 혼합, 단순 사용과 학습의 차이,
역할 배정과 수행 행동의 차이, 사용자 관점, 데이터 안의 AI 지시, 제외 조건이 있는 복수 역량을 다룬다.
원문에는 팀/타인/본인, 부정/계획/혼합/가정, 결과의 0건, 시기·반복과 소회를 포함했다.

원문 추출은 종류·주체·진술 상태·issue를 구간별로 따로 진단한다. 응답 하나가 실패해도 다른 구간의
계약상 유효한 판단은 진단 점수에 남기며, **필수 검증 통과 여부는 응답 전체 기준**으로 유지한다.
이 채점 방식과 정답 일부가 달라졌으므로 v2 추출 점수와 단순 차감해 모델의 개선 폭이라고 주장할 수 없다.

새 사례도 같은 개발 보조 도구가 작성했으며 규모가 작다. 사람 검토와 새로운 도메인·문항으로의 일반화 확인이 필요하다.
문항·매칭 종합 점수에 추출 점수를 합치지 않는다. 추출 모델의 적합성을 별도로 확인한다.

현재 고정한 초안은 `prepare-evaluation-v3.py`의 재실행으로 덮어쓸 수 없다.

전체 코드 테스트 **197개 통과**를 확인했다. 추가된 10개는 제외된 지시문 처리, 혼합 상태의 fact 차단,
구간별 오류 진단, 중복 ID 거부, 출력 상태의 모순 차단, 원문 종류에 없는 fact 오채택,
새 사례 분리와 정답 미전송, custom 표현 변형의 범위를 검사한다. 모의 테스트 성적은 실제 모델 성적으로 쓰지 않는다.

모든 모델에 같은 문항 24개·경험 판단 44개·원문 53구간을 사용했다.

| 모델 | 문항 전체 일치 | 경험 판단 전체 일치 | 종합 점수 | 추출 구간 전체 일치 |
|---|---:|---:|---:|---:|
| Gemma 4 26B A4B | 91.67% | 63.64% | 77.65 | 83.02% |

| Qwen3-14B | 87.50% | 45.45% | 66.48 | 69.81% |
| Qwen3.5-9B | 83.33% | 45.45% | 64.39 | 54.72% |

Gemma 12B는 새 원문 20구간 중 18개, Gemma 26B는 17개가 전체 일치했다.
두 모델의 추출은 12개 요청의 계약 검증을 통과했고, 정답에서 허용하지 않은 fact를 채택한 사례가 0개였다.
이는 추출의 필수 검사를 통과했다는 뜻이며 문항·매칭 품질이나 사람의 최종 승인을 대신하지 않는다.

문항·매칭 필수 검사는 네 모델 모두 통과하지 못했다. 다만 오류의 의미를 구분해야 한다.
Gemma 26B의 문항 감점 2건은 ‘사용자 관점의 제안’, ‘사용자 관점의 개선 제안’이 등록된 label과 정확히 다르기 때문이다.
원문 인용은 맞고 해석도 타당해 보이지만, **실행 이후 정답 표현을 늘려 이번 점수를 올리지는 않았다.**
Gemma 12B에도 ‘사용자 관점의 개선’이라는 표현 차이가 있었고, 다른 사례에서는 문제 해결 기준을 추가했다.
해석이 다른 오류와 표현만 다른 사례를 사람이 구분해 검토해야 한다.

Gemma 26B의 사용 불가 fact 채택 1건은 ‘저는 팀원이었습니다.’를 구체적인 본인 ROLE로 허용한 경우다.
이 지표를 팀 행동을 본인 행동으로 조작했다거나 AI 지시를 실행했다는 뜻으로 확대하면 안 된다.
구체적인 담당 범위가 없는 소속 진술을 ROLE 근거로 인정할지에 대한 기준 검토가 필요하다.

보완 설정 B의 협업·학습 시연 8건 중 5건이 완료됐다. Qwen3.5 협업과 Qwen3-14B 두 문항은 중복 근거 등의
응답 검증 오류로 중단됐다. Gemma 26B는 두 문항 모두 완료하고 팀 성과만 기록된 경험을 확인 필요로 반환했다.
Gemma 12B 학습 시연은 학습이 명시되지 않은 API 경험도 직접 부합으로 판단했다. 추출 점수가 높아도 매칭에 그대로 사용할 근거는 부족하다.

## 성능 저하 확인과 이전 설정 A 비교

Qwen의 기존 개발 사례 매칭 점수가 낮아져, 이전 프롬프트·출력 제약을 그대로 가져온 설정 A를 추가 비교했다.
이는 새 사례 결과를 일부 확인한 뒤 결정한 후속 비교이며 처음부터 사전 등록한 A/B 실험은 아니다.
정답·입력·현재 검증 코드·현재 채점 코드는 동일하게 유지하고, 프롬프트·출력 스키마·그 메타데이터만 바꿨다.
기존 설정은 `output/review-v3-20260909/baseline-runtime/`에 격리했으며 세 소스 파일의 차이를 확인했다.
새 자료에서 측정하는 것이므로 이전 보고서의 16문항/33구간 점수와 혼동하면 안 된다.

26B의 첫 실행은 GPU 메모리가 거의 찬 상태에서 일부 요청이 약 50초까지 지연돼 중단했다.
첫 실행의 26B 기록과 로그 초기에 종료된 재시도는 최종 성적에 포함하지 않았다.
최종 26B 실행은 메모리 여유 목표 4,096MiB로 별도 수행했고, 같은 조건을 설정 A의 26B에도 적용했다.
다른 세 모델은 1,536MiB다. 컨텍스트·출력 길이·샘플링 설정은 그대로다.
다른 앱의 GPU 사용량이 변했으므로 요청 시간만으로 설정이나 모델의 속도 우위를 단정하지 않는다.

다음 표의 A/B는 **동일한 v3 입력·정답·채점 코드**의 비교다. 정답 파일과 입력 파일의 동일성을 대조했고,
정책·추출 기준은 프롬프트 변경에 따른 protocol 해시만 다르다. 실행 코드의 차이는 프롬프트·출력 제약·메타데이터 3개 파일이다.
첫 B의 세 모델 실행 뒤 메모리 여유를 인자로 받는 기능을 실행기에 추가했지만, 세 모델의 실제 여유 목표는 A/B 모두 1,536MiB다.

| 모델 | 문항·매칭 종합 A → B | 추출 전체 일치율 A → B | 새 원문 20구간 일치율 A → B |
|---|---:|---:|---:|
| Qwen3.5-9B | 74.24 → 64.39 | 54.72% → 54.72% | 60% → 65% |
| Qwen3-14B | 74.62 → 66.48 | 69.81% → 69.81% | 70% → 70% |
