# C01 실제 모델 비교·API 시연 결과

**후속 보완:** [9월 18일 새 사례 재평가](w4-c01-domain-evaluation-2026-09-18.md)에서 기업 판단 지침을 보완하고 기존 달리기 오연결의 실제 API 회귀를 통과했다. 새 사례의 모델 오류는 남아 있어 운영 선정은 계속 보류다. 아래는 보완 전 실행 기록이다.

2026-09-17. **로컬 모델 4개의 실제 비교와 API 시연을 완료했다. Gemma 12B가 이 작은 분리 평가에서 가장 좋았지만, 실제 통합에서 기업 기준 오연결이 남아 운영 모델 선정은 보류한다.**

W1 백엔드도 최신 코드를 확인했다. API와 저장 구조는 준비됐지만 W4 실행기, ID·상태 변환, 상세 결과 저장과 게시 검사가 추가로 필요하다. [백엔드 연결 계획](w4-w1-bridge-plan-2026-09-17.md)에 실제 DTO 대조와 팀 확인 항목을 적었다.

## 실제 실행 범위

- RTX 5080의 기존 GGUF 모델 4개와 해시가 고정된 llama.cpp b10859를 사용했다.
- 가상 경험 3개, 원문 구간 15개, 문항 2개(전문성·직무 경험), 가상 기업 Source 2개다.
- 모델마다 추출 3회·판단 6회, **36회 실제 호출**을 했다. 이후 선택한 조합의 W4 API에서 추출 3회·판단 3회를 새로 호출해 **총 42회**다.
- 판단 비교에서는 추출 정답 초안으로 구성한 입력을 사용해 추출 오류와 판단 오류를 분리했다. 실제 API 시연에서는 추출부터 새 모델 응답을 사용했다.
- W4 FastAPI 경계와 로컬 모델 HTTP는 실제로 실행했다. W1 사용자·프로젝트 조회와 W3 상태는 가상 구현이다. 실제 W1·W2 서비스와의 전체 통합은 실행하지 않았다.

모든 모델의 비교 요청은 JSON을 반환했다. JSON 형식이 정상이라는 사실만으로 의미·근거가 정확하다고 채점하지 않았다. 모델마다 동일한 생성 설정과 입력을 사용했으며 반복은 1회다. 모델을 한 번에 하나씩 적재했고, `fit-target`은 6144 MiB였다. 이번 결과는 속도 벤치마크가 아니다.

## 교정 후 분리 평가 점수

| 모델 | 원문 구간 분류 | 문항 상태 | 기업 진술 연결 | 복합 요건의 개별 조건 | 인용 근거 충족 |
|---|---:|---:|---:|---:|---:|
| Qwen 3.5 9B Q4 | 46.67% | 91.67% | 66.67% | 100% | 91.67% |
| Qwen 3 14B Q6 | 66.67% | 91.67% | 66.67% | 100% | 86.11% |
| **Gemma 4 12B QAT** | **86.67%** | **100%** | **100%** | **100%** | **100%** |
| Gemma 4 26B A4B QAT | 73.33% | 91.67% | 83.33% | 83.33% | 86.11% |

원문 분류는 구간의 종류·주체·긍정/부정 등 서술 상태·문제 표시가 정답 초안과 모두 일치한 비율이다. 원문을 그대로 복사하는 코드의 정확도를 LLM 점수로 계산하지 않았다. Fact로 잘못 편입할 수 있는 분류는 Qwen 9B 4건, Qwen 14B 2건, 두 Gemma 0건이었다. 정답 초안의 라벨 자체는 사람 검토 전이다.

문항 상태는 12개, 기업 진술 연결은 6개, 개별 조건은 18개, 인용 근거는 36개 판단을 분모로 삼았다. 두 Source의 같은 의미 조건은 하나로 세되 둘 모두 맞아야 정답이다. 실패·누락된 호출도 분모에서 빼지 않는다. 이 점수들을 합산해 종합 점수를 만들지 않았다.

Qwen 두 모델은 전문성 문항에서 기술 학습과 관련 없는 경험을 기업의 기술 학습 진술에 연결한 경우가 각각 2건 있었다. 코드가 합산한 AND/OR 최종 조건 정확도는 Qwen 9B·Gemma 12B 100%, Qwen 14B·Gemma 26B 83.33%였다. 모델의 조건 상태가 맞아도 인용한 근거가 본인 행동을 뒷받침하지 않으면 코드가 판정을 낮출 수 있다.

### 채점 기준을 교정한 이유

초기 기준은 직무 행동 근거 `u3`와 함께 본인 역할 `u1`을 인용하면 감점했다. 역할은 실제 행동의 맥락이므로 이 제한은 잘못이었다. 필요한 행동 근거를 계속 요구하면서 역할 문장도 함께 인용할 수 있도록 고쳤다. 역할만 인용한 답은 여전히 근거 충족으로 인정하지 않는다.

원래 호출·점수는 `run-1`에 보존했다. 같은 응답 36개를 교정 기준 0.2로 다시 채점한 결과가 `rescore-2`다. **재채점은 새 호출이나 새 사례 검증이 아니다.** 모든 모델에 동일하게 적용했고, 입력·프롬프트·모델이 달라지면 재사용을 거부하는 검사도 추가했다. 새로운 사례에서 이 기준을 검증하는 작업은 남아 있다.

## 실제 추천 API에서 확인한 결과

분리 평가의 필수 검사를 통과한 Gemma 12B를 추출과 판단 양쪽에 사용했다. API는 HTTP 200, `w4-detailed-output/0.3`, `COMPLETED_WITH_LIMITATIONS`를 반환했다.

| 순위 | 경험 | 문항 판정 |
|---|---|---|
| 1 | 6주간 JSON Schema 학습 후 파일 업로드 검증에 적용 | DIRECT_MATCH — 학습 분야·지속 과정·실제 적용 모두 근거 있음 |
| 2 | 개인 달리기 훈련 | NEEDS_CONFIRMATION |
| 3 | 과학관 체험 부스 협력 | NEEDS_CONFIRMATION |

**통합 품질 감사는 실패했다.** 달리기 경험의 다음 문장을 기업의 “꾸준히 기술을 학습한 경험”과 연결했다.

> 저는 두 달 동안 매주 훈련 기록을 비교하고 속도를 조정하며 반복해서 연습했습니다.

이 문장은 지속적인 훈련을 보여 주지만 기술 학습의 근거는 아니다. 같은 진술이 두 가상 Source에 있어 잘못된 링크 2개가 생겼다. 영향을 받은 경험은 달리기 1개다. 1순위와 문항 상태가 맞더라도 이 추천 이유를 그대로 신뢰할 수 없다.

분리 평가의 판단 입력과 실제 추출 결과를 사용하는 통합 입력은 다르다. 이 차이와 모델 응답 변동이 오판에 미친 영향은 추가 확인이 필요하다. 분리 평가 100%를 통합 품질 보장으로 사용하지 않는다.

최종 응답의 후보 누락·문항 상태·기업 오연결을 검사하는 품질 감사 함수를 추가했고 이 사례를 실패로 기록했다. **이것은 고정 가상 시연을 감사하는 검사다. 서비스 모델의 의미 오판을 일반적으로 해결한 것은 아니다.** 운영 모델은 계속 `WITHHELD`다.

새 테스트는 누락 호출의 분모 유지, Source 중복 집계 방지, 엉뚱한 근거, 역할 맥락 허용, 역할만으로 행동 대체 금지, 다른 입력으로 재채점 금지, 성공 응답 속 잘못된 기업 연결을 확인한다. Ruff F 검사도 통과했다. 최초 감사 테스트의 임시 SQLite 접근 문제와 필드명 오류를 확인한 뒤 수정·재실행했으며 최종 결과는 `regression-3`이다.

이번 작업은 평가 실행기·평가 기준·테스트·문서에 추가했다. 실제 호출에 사용한 엔진의 C01 프롬프트와 추천 로직은 이번 결과에 맞춰 변경하지 않았다. 실행 당시 소스는 각 실행 폴더에 보존되어 있다. 실제 추론 이후 추가한 품질 감사는 별도 감사 파일과 코드 해시로 식별한다.

```powershell
# 새로운 실제 4모델 비교. 출력 폴더는 새 이름이어야 한다.
.\.venv\Scripts\python.exe scripts/run-c01-evaluation.py --output-dir output/c01-live-new

# 같은 입력으로 저장된 응답 재채점 + 통과 조합의 새 API 호출.
# 재채점만 하는 명령이 아니며 마지막 API 단계는 실제 모델을 호출할 수 있다.
.\.venv\Scripts\python.exe scripts/run-c01-evaluation.py --output-dir output/c01-rescore-new --rescore-from output/c01-model-evaluation-20260917/run-1
```

실행에는 등록된 모델 파일과 llama.cpp 실행기가 필요하다. TEMP의 실행기가 없으면 `--runtime`으로 준비한 실행기를 지정한다. 서버가 시작할 때 모델 파일의 해시를 확인한다. 실제 개인정보 전송 제한을 풀거나 상용 API 키를 설정한 작업은 없다.
